1. Executive Summary & Abstract

Timely access to safe, compatible blood units during acute traumatic hemorrhage, elective cardiac surgeries, and oncological treatments is among the most severe logistical challenges in contemporary emergency medicine. Traditional blood acquisition networks suffer from high latency due to static, unverified donor directories, lack of real-time donor availability awareness, and widespread public misunderstanding regarding biological ABO and Rh blood group compatibility.

LifePulse is an enterprise-grade emergency blood donor network and hospital fulfillment platform. Built with a high-performance Python 3 Flask backend and an embedded SQLite3 relational database, LifePulse introduces an automated Biological Compatibility Engine, Dynamic Presence Toggling (allowing donors to switch between Available and Unavailable via asynchronous REST calls), an Interactive Leaflet GIS Map for spatial proximity identification, and an Emergency Fulfillment Tracking System where hospital staff can monitor pledged donor units in real time.

2. Problem Statement & Clinical Motivation

Clinical Core Challenge: In hemorrhagic shock, transfusion delays exceeding 60 minutes ("the Golden Hour") increase patient mortality by over 40%. Static spreadsheets and social media appeals fail because over 80% of listed numbers are unreachable, offline, or biologically incompatible.

Current mechanisms exhibit three fundamental operational flaws:

  1. Absence of Presence Status: Existing donor lists do not track if a volunteer is currently working, ill, or traveling, resulting in frustrating dead-ends during critical midnight emergencies.
  2. Biological Matching Inefficiencies: Search portals typically look only for identical blood groups. For example, an $A^+$ patient in urgent need can safely receive $A^+$, $A^-$, $O^+$, and $O^-$ red blood cells; failing to identify compatible universal donors costs valuable lives.
  3. Opaque Fulfillment Tracking: Multiple community donors often mobilize to the same facility for a single patient because there is no synchronized ledger displaying how many units have already been pledged or completed.

4. Mathematical Formulations & Algorithmic Design

4.1 Geodesic Spatial Distance: The Haversine Formulation

To compute spatial proximity between the patient's hospital $(\phi_1, \lambda_1)$ and candidate donors $(\phi_2, \lambda_2)$ without external fee-based APIs, the platform implements the Haversine equation over Earth's mean spherical radius ($R = 6371.0 \text{ km}$): 

Δφ = radians(lat2 - lat1)
Δλ = radians(lon2 - lon1)
a = sin²(Δφ/2) + cos(radians(lat1)) * cos(radians(lat2)) * sin²(Δλ/2)
c = 2 * atan2(√a, √(1-a))
distance_km = R * c

5. Database Architecture & Entity-Relationship Schema

The system operates across 5 normalized relational tables in blood_donor.db:

5.1 Table: users (Authentication & Account Profiles)

Stores credentials and clinical parameters for donors and hospital coordinators.

  • id (INTEGER, Primary Key, Auto Increment)
  • name (TEXT, Not Null): Full legal name / organization title
  • email (TEXT, Unique, Not Null): Login identifier
  • password_hash (TEXT, Not Null): Salted PBKDF2:SHA256 digest
  • role (TEXT): 'donor' or 'hospital'
  • blood_group (TEXT): Clinical blood type
  • phone, city, state (TEXT): Emergency contact & geography
  • last_donation_date (TEXT): Used for clinical 56-day recovery interval
  • is_available (INTEGER): 1 = Available, 0 = Temporarily Offline

5.2 Table: urgent_requests (Hospital Emergency Board)

Stores broadcasting emergency cases matching the project reference screenshots.

  • id (INTEGER, Primary Key): e.g. Case #1 (John Doe), Case #2 (Alice Wong), Case #3 (vijay)
  • patient_name (TEXT, Not Null)
  • blood_group (TEXT, Not Null)
  • units_needed (INTEGER, Not Null)
  • units_fulfilled (INTEGER, Default 0): Pledged unit accumulator
  • urgency_level (TEXT): 'CRITICAL NEED', 'HIGH NEED', 'MEDIUM NEED'
  • hospital_name, city, hotline (TEXT)
  • status (TEXT): 'ACTIVE' or 'FULFILLED'

5.3 Table: request_responses (Volunteer Pledges Ledger)

Enforces transactional tracking when a donor clicks "Volunteer / I Can Donate".

  • id (INTEGER, Primary Key)
  • request_id (INTEGER, Foreign Key → urgent_requests(id))
  • donor_name, donor_email, phone, blood_group (TEXT)
  • units_pledged (INTEGER, Default 1)
  • status (TEXT): 'PLEDGED', 'COMPLETED'

8. Top 10 Viva Voce Oral Questions & Model Answers

Q1: Why did you choose Python Flask over Django or Spring Boot?

Answer: Flask is a lightweight WSGI micro-framework with sub-millisecond route dispatching and minimal memory overhead. For a medical emergency network where immediate request processing is paramount, Flask avoids the unnecessary monolithic boilerplate of Django while giving full control over the REST API layer.

Q2: How does the system prevent hemolytic transfusion reactions?

Answer: Hemolytic transfusion reactions occur when recipient antibodies agglutinate foreign red blood cell antigens. Our backend incorporates a directed graph in app.py mapping safe donor-to-recipient pathways. For instance, $AB^+$ patients lack anti-A and anti-B antibodies, qualifying them as Universal Recipients, whereas $O^-$ erythrocytes have neither A nor B antigens, qualifying them as Universal Donors.

Q3: How are passwords secured in the database?

Answer: Passwords undergo salted key derivation using PBKDF2 with HMAC-SHA256 across 1,000,000 iterations. Plaintext passwords are never stored; verification uses constant-time comparison (check_password_hash) to eliminate side-channel timing attacks.

Q4: How does spatial search operate without costly Google Maps billing?

Answer: Distance is calculated server-side using the trigonometric Haversine Formula on latitude/longitude pairs. The frontend renders these coordinates on interactive OpenStreetMap tiles via Leaflet.js, an open-source mapping engine requiring zero API keys and zero vendor lock-in.

Q5: What happens when an urgent request is fully pledged?

Answer: When a donor pledges blood via /api/respond-urgent, the units_fulfilled counter increments. When units_fulfilled >= units_needed, the system updates the record status to 'FULFILLED', turning the progress bar green and notifying attending hospital staff.
